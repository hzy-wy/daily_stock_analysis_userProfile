# 性能、并发与响应链路审查

本次审查覆盖 API 鉴权、任务队列、股票导入、Agent 会话、回测、任务事件流、Web 首页刷新，以及已有的数据源、行情看板、分析流水线和技术指标实现。审查基于当前本地工作树开展，并保留进入任务前已有的未提交修改。

## 结论

技术指标计算已经使用 Pandas 的 rolling/ewm 等向量化实现，没有发现需要改变金融计算口径才能解决的 CPU 热点。影响用户响应的主要因素是同步数据库或解析工作占用 ASGI 事件循环、长回测占用普通 HTTP 请求、任务和 SSE 缺少背压、页面在不可见或旧请求未完成时继续刷新，以及并发请求返回顺序不确定。

本轮已完成以下收敛：

| 链路 | 原问题 | 当前行为 |
| --- | --- | --- |
| 鉴权和管理 API | 密码校验、SQLite 会话/用户/审计访问在事件循环内运行；直接并行又可能破坏首次设置和凭据更新顺序 | 同步端点进入工作线程，并通过单独的串行容量限制保护凭据变更；中间件的会话解析和审计也移出事件循环 |
| 多用户初始化 | `has_owner` 在热请求中重复执行权限种子逻辑；legacy 缓存可能错误绕过显式 multi-user 模式 | 复用一次性 `ensure_ready`，Owner 查询保持实时；显式 multi-user 模式不再受旧认证缓存影响 |
| Agent 与股票导入 | 执行器构造、会话数据库访问、CSV/Excel/文本解析阻塞其他请求 | 使用线程池执行；上传读取使用异步接口，并继续按上限多读 1 字节判断超限 |
| Agent 流式响应 | 慢客户端会令线程持续创建未完成的跨线程 `queue.put` Future，事件和 Future 都可能无界累积 | 每条流最多缓存 128 个事件；普通增量只保留最近事件，完成或错误事件会清空旧增量并优先送达 |
| 分析任务准入 | 并发提交可让进程内待处理任务持续增长；批量请求可能部分入队 | 活跃任务总量限制为 100；批量提交在锁内先去重、再整体检查容量，超限返回 HTTP 429 和 `Retry-After: 30` |
| 任务列表 | 先截断再筛状态，活跃任务可能被大量历史任务挤出 | 先按用户和状态过滤，再应用 limit |
| SSE 任务事件 | 快照发送后才订阅会遗漏完成事件；慢浏览器可令事件队列无界增长 | 在首次响应前订阅；每个连接最多缓存 256 个事件，溢出后发送 `resync_required`，前端重新拉取权威状态 |
| 回测 | Web 等待同步 `/run`，大数据量时容易触发 HTTP 超时；重复点击会提交等价重任务 | Web 使用 `POST /run/async`，按任务号轮询；同一用户、同一参数范围只运行一个回测，四小时客户端截止后给出明确超时；离开页面会取消浏览器侧轮询和迟到状态更新 |
| 回测页面读取 | 汇总失败会阻止结果列表；总览和单股表现串行；旧筛选响应可覆盖新筛选 | 结果列表独立加载，总览和单股并行；使用请求序号丢弃迟到响应，保留成功的部分数据 |
| 首页后台刷新 | 隐藏页面仍周期请求；定时器和 visibility 事件会叠加 | 页面隐藏时暂停；定时和恢复可见共享一个进行中标志，并发刷新使用 `allSettled`，单项失败不锁死后续刷新 |

同步 `POST /api/v1/backtest/run` 保留给现有客户端；Web 默认走异步接口。异步任务状态保存在当前服务进程内，服务重启后任务号失效，但已经成功写入数据库的回测结果不会回滚。

## 架构边界

- `src/core/pipeline.py` 的股票分析使用有限线程池，LLM 并发也有保守上限；继续增加线程只会把压力转移给模型、行情源和 SQLite。
- `data_provider/base.py` 已有阶段预算和超时工作槽。Python 线程超时不能强制终止正在第三方库内部阻塞的调用，生产环境仍应监控各数据源超时率和存活线程数。
- `src/services/market_light_service.py` 已使用分块并行、同键请求合并、总预算和陈旧缓存。缓存与合并目前按进程生效。
- 任务、SSE 订阅及部分缓存仍是进程内状态。横向多实例部署前，需要把任务状态、幂等键和事件分发迁移到共享基础设施；仅增加 Uvicorn worker 会让客户端轮询落到不同进程并返回 404。
- 回测和股票分析目前共享有限执行器，因此具备总并发上限，但长回测会占用一个分析工作槽。若生产监控确认回测持续挤压交互式分析，再拆分独立队列，并为两类队列分别设置容量和外部调用预算。
- SQLite 适合当前单机部署。写并发继续增长时，应先记录锁等待和事务时长，再评估 WAL 参数或外部数据库，避免在没有容量数据时迁移基础设施。

## 可复核性能证据

`scripts/benchmark_api_responsiveness.py` 用固定 25ms 同步鉴权工作模拟 1、5、20 个并发请求。该基准关注事件循环是否还能服务健康检查，不代表真实数据库吞吐量。

| 并发 | 修改前最大事件循环延迟 | 工作线程方案最大事件循环延迟 |
| ---: | ---: | ---: |
| 1 | 22.55ms | 17.44ms |
| 5 | 125.65ms | 14.28ms |
| 20 | 513.83ms | 14.64ms |

鉴权事务仍按设计串行，因此批次完成时间基本不变；改善的是同进程其他请求不再随鉴权排队一起失去响应。原始本地产物位于 `.claude/reviews/api-responsiveness.json`，该目录按仓库规则不作为产品文件提交。

## 生产验收建议

上线时至少记录 API p50/p95/p99、事件循环延迟、活跃/拒绝任务数、队列等待时间、SQLite 锁等待、每个数据源的超时和 fallback 次数、LLM 首 Token/总耗时、SSE 重同步次数。按 1、5、20 个并发用户逐级放量；只有这些指标稳定，才能给出真实提速比例和容量结论。

本轮不需要数据库迁移或新增配置。回滚时只需撤销本轮列出的 API、任务队列、Web 生命周期/回测代码、测试和文档，保留工作区原有修改。本文是中文专项审查，没有独立英文版；用户可见的回测 API 变化已同步到中英文完整指南。
